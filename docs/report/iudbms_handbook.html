00The problem

USB has trusted devices by default since 1996. A device self-reports its Vendor ID, Product ID and interface descriptors at enumeration, and the host accepts these claims with no cryptographic verification at all.

BadUSB attacks exploit exactly this. Firmware is altered to declare an interface it doesn't honestly represent — almost always an HID keyboard — so something that looks like an ordinary flash drive or cable can inject a pre-programmed keystroke payload the instant it's plugged in. Because keyboard input is inherently trusted, this bypasses file-based antivirus entirely and executes within seconds.

Every existing defence — allowlisting by VID/PID, user role-confirmation, static kernel filter rules — verifies identity at connection. None of them judge how a device actually behaves once it's running, so a device that spoofs an allowed identity, or misbehaves inside an approved role, defeats them completely. IUDBMS's whole premise is to trust devices by observed behaviour instead.

01Where this sits in the literature

Three separate research strands, none of which overlap on their own. Condensed from the Review 1 paper's literature review.

The three strands, and what each one does and doesn't cover
StrandKey worksEstablishesLeaves open
USB / BadUSB defencesWMUD [1], SafeUSB [2] Tamper-resistant allowlisting; userspace behavioural keystroke monitoring Identity-bound (WMUD); ~1s userspace activation delay lets short payloads succeed (SafeUSB)
eBPF kernel observabilityeIDPS [3], Rajurkar&Deshmukh survey [4], Song survey [5] Kernel-extract / userspace-infer as the dominant pattern for fast, verified in-kernel ML Applied almost exclusively to networks — never to USB, where the natural unit is the URB
LSTM temporal anomaly detectionLSTM-AE [7], Baek&Jung [6], Saini et al. [8], attention-LSTM [9], IIoT-LSTM [10] Layered LSTM designs catch multi-stage, zero-day behaviour in real time Never applied to a single USB peripheral's own event stream

IUDBMS's stated position: not a new technique in any of the three strands individually — the paper is explicit that eBPF capture, unsupervised anomaly scoring, and LSTM temporal modelling all already exist elsewhere. The claimed novelty is combining them into one per-device, closed-loop pipeline, and pointing that pipeline at USB specifically — which no eBPF-ML work and no USB-defence work has done.

02The scorecard — four claims, checked against our own evidence

The paper (§3.3) makes four specific novelty claims. This project has spent the build phase running ablations that directly test each one. Two hold up. Two don't.

N1 — Multi-modal feature fusion

Refuted by our own ablation

“Fuses event timing, traffic volume, and descriptor changes into one feature stream… answering the network-only gap.”

Built as stated — 28 deployed features across four modalities (timing, payload, protocol, identity), fused into one vector. But holding each modality out one at a time and testing it alone shows fusion isn't earning its keep:

Modality aloneWindow AUCSession detection
Timing (9 features)0.966277.5%
Payload (8 features)0.975290.8%
Protocol (6 features)0.945877.5%
Identity (6 features)0.888439.2%
All 28 fused (deployed)0.976289.2%

The payload modality alone reaches 90.8% — a full point higher than the fully fused model. Fusion adds essentially nothing measurable on this corpus, because payload sequence novelty (the feature that catches most attacks) is already strong enough on its own.

N2 — Per-device adaptive behavioural baselines

Refuted by our own ablation

“Each device is scored against its own learned norm rather than a global rule set, answering the identity-bound trust gap left by WMUD.”

Built exactly as described — an online EWMA baseline per device, fused 45% into Stage 1's score alongside the class-conditioned Isolation Forest. Setting that weight to zero (forest only, same score scale) isolates its contribution:

ConfigurationWindow AUCSession detection
Full system0.976289.2%
Forest only, no device baseline0.975590.8%
Stage 1 with baseline0.884715.8%
Stage 1, forest only0.88760.0%

Removing the per-device baseline changes detection by less than a session either way, and its window-level AUC contribution is negative at both rows. Likely explanation, offered as hypothesis: the forests are already class-conditioned, so a device's class-specific normality is largely captured at the population level, leaving little for a per-device term to add — at least on a corpus where devices within one class are close to identical.

N3 — Closed-loop kernel-level enforcement

Not built as specified

“Verdicts… execute inside the kernel with no userspace round-trip, answering SafeUSB's activation-latency limitation.”

This is the one claim we can't score with an ablation, because the described mechanism — in-kernel eBPF enforcement — was never built. What exists is a userspace Python policy engine that generates the correct rule (echo 0 > /sys/bus/usb/devices/<dev>/authorized) and the correct trigger logic, but never executes it. A module-level constant, ENFORCEMENT_REVIEWED = False, sits in front of every execution path and raises rather than writing to sysfs. This was a deliberate safety choice, not an oversight — but it means the activation-latency gap the paper set out to close is currently closed only on paper, not in the kernel fast-path the paper specifically describes.

N4 — Temporal sequence modelling

Strongly supported

“A userspace LSTM analyses rolling event windows to catch slow-escalation attacks single-point detectors miss, bringing temporal modelling to USB for the first time.”

This is the pillar the evidence backs most clearly. Stage 1 alone (memoryless, one window at a time) detects 15.8% of attack sessions. Adding the LSTM's 10-second rolling context takes that to 89.2% — a 5.6× improvement that shows up consistently across every corpus size and every fix made this session.

One caveat worth being precise about: a separate comparison (§7, finding 15) tested GRU, a 1-D CNN, and gradient boosting against the LSTM, all fed the identical 10-window sequence. All four landed within one session of each other. Sequence context is the pillar that matters — recurrence specifically, or LSTM specifically, is not uniquely justified by this evidence. The paper's claim should be read as "temporal modelling," which holds, rather than "LSTM architecture," which is one of several equally-good ways to consume that same sequence.

The honest one-paragraph summary

Of four claimed contributions, one (N4, temporal modelling) is strongly supported by direct measurement; one (N3, kernel-level enforcement) was never actually built and remains a design on paper; and two (N1 fusion, N2 adaptive baselines) were built exactly as specified and then measured to contribute nothing on this corpus once properly isolated. That last part — building something, then finding your own ablation doesn't support it, then reporting that plainly instead of hiding it — is itself the project's strongest methodological asset, and is documented in full in Section 7.

03Architecture — designed vs. built

The paper specifies a four-layer pipeline (§4, Objectives 1–4). Here's each layer exactly as designed, next to what actually exists.

L1
In-kernel eBPF capture Designed: an eBPF program at the kernel/driver boundary intercepting URBs via usb_submit_urb/__usb_hcd_giveback_urb, passing compact records through shared BPF maps.  Built: a usbmon (debugfs) text-log reader in userspace Python — explicitly framed in the paper itself as an acceptable fallback, "the design is agnostic to this choice." Fully working and fixture-validated against real kernel line formats; eBPF is deferred (plan's own designated sacrifice week).
L2
In-kernel anomaly scoring Designed: per-device baseline + Isolation Forest, running in the kernel fast-path.  Built: Isolation Forest + EWMA baseline exactly as specified algorithmically — but running in userspace Python, not the kernel. One-Class SVM (the paper's named alternative) was tested and found degenerate (AUC 0.44, alerts on everything) — Isolation Forest was the right call.
L3
Userspace temporal sequence modelling Designed: a PyTorch LSTM over rolling event windows.  Built: exactly this — the most faithfully implemented layer relative to the paper. 10-window sequences, PyTorch, trained with onset-based transition labelling.
L4
Closed-loop kernel-level enforcement Designed: verdicts execute inside the kernel, no userspace round-trip.  Built: a correct escalation ladder and rule generator in userspace Python — but every execution path is dry-run only. Nothing has ever been written to sysfs.
L5
Data store and interface Designed: SQLite persistence of baselines/event history/alerts, exposed via a FastAPI/Flask dashboard.  Built: closely matches — SQLite with five tables, FastAPI, a working dashboard. Gap: "event history" in the plan's own words meant raw traces; the database stores only post-extraction feature vectors, never raw URBs (see §4). The baselines table is currently empty — it's populated by the live streaming detector, which has been run against a replayed recording but never against a real host.

The evaluation methodology, separately from the four layers

The paper's Objective 6 specifies evaluation against Pi Pico / Digispark hardware attacks, measuring detection rate, false-positive rate, enforcement latency and throughput overhead, compared against an identity-based baseline. The metrics measured match this almost exactly — detection rate, benign FP rate, latency, and an identity-whitelist baseline are all in Section 6. What doesn't match: zero of it comes from real hardware. Every session, benign and malicious, is generated by a simulator. This is the single largest gap between the paper's evaluation plan and what has actually been measured.

Ten session profiles

Five benign — keyboard, mouse, mass_storage, webcam, audio — each with its own realistic timing model (human keystrokes drawn log-normal, mouse motion bursts, bulk file-copy patterns). Six attack — hid_injection (fast robotic typing), identity_switch (enumerates as storage, grows a keyboard interface mid-session), staged_delay (human-like for ~47s, then fires), class_exfil (declares HID, sends bulk data), mimicry (human-paced but loops a short script), mimicry_adaptive (human-paced, types a real payload once — the hardest case, see §7).

Every one of those 62,791 rows is synthetic

No physical device, no Rubber Ducky, no real usbmon capture feeds any of this. The raw-line format is real and validated against kernel documentation, but the content — every timestamp, every byte count, every keystroke — is generated by src/iudbms/capture/simulator.py. This is the single biggest asterisk on every number in this document, and it's the reason the paper's own hardware-evaluation objective (§4, Objective 6) remains unmet.

Nothing raw ever reaches the database

The five SQLite tables (devices, windows, baselines, alerts, actions) store only post-extraction feature rows, model scores, and generated rules — never a raw URBEvent. This diverges from the plan's own stated intent to "store raw traces, not just features, so the feature set can be revised without re-collecting" — that raw-trace archive was specified but never built.

05The algorithm — from one second to one decision

Full formulas and parameter values live in the companion iudbms_algorithms.html reference. This section is the conceptual chain that connects them.

1
Stage 1 — memoryless, per-second Two questions fused per window: an Isolation Forest asks "unusual for this device's declared class?" (trained once, offline, benign windows only); an online EWMA baseline asks "unusual for this specific device's own history?" Fused 55%/45%, output one number 0–1.
2
The relay, not a vote Stage 1's number is appended as a 29th input dimension — it never independently votes. Every second's score is forwarded unconditionally, whether suspicious or not; there is no gate between the two stages.
3
Stage 2 — a 10-second LSTM Reads the last 10 rows of 29 numbers as one sequence, left-padded by repetition, strictly causal. Outputs one continuous number: P(this window is part of an attack). Trained with onset-based labelling — pre-onset windows of a malicious session are labelled benign — which is what forces the model to key on the transition, since the same device sits on both sides of that boundary.
4
Threshold — calibrated, not guessed A held-out calibration split (140 sessions, touched by neither training nor final reporting) is scored by the frozen models; every benign score is sorted, and the value at the 99.99th percentile becomes the threshold (target FPR = 0.0001 → threshold = 0.9916). Frozen from that point on — never re-derived from test or live data.
5
The persistence gate A single second crossing the threshold does nothing. A rolling 6-second window tracks hits; 4-of-6 → THROTTLE (severity high); 8 cumulative hits → DEAUTHORIZE (severity critical). This absorbs the noisy, near-threshold flicker visible in every live demo run.

07The audit trail — sixteen defects found and fixed

The project's working method: build, adversarially attack it, report what breaks including the embarrassing parts, fix it, state plainly what remains unfixed. Every finding below changed a reported number.

Capture layer

The parser silently dropped four real usbmon line forms

Control setup packets, every submission line, uncaptured payloads, and multi-part iso status words all vanished with no counter. Also read the polling interval as the transfer length. Both fixed and fixture-tested against real kernel documentation.

Corpus fidelity

A duration leak survived being fixed once

Aggregate durations matched (63.7s benign vs 63.9s malicious) — looked clean. Per profile, staged_delay drew from a different range entirely. The audit now runs per profile, and a test re-introduces the bug to prove the audit still catches it.

Stage 1

Three features exactly constant across benign traffic exploded a standardised score to ~10⁶

Found by the dashboard rendering alert evidence as late_iface_flag 4472091.23. Fixed with a variance floor and clip. Collapsed Stage-1-only detection from 44.2% to 11.7% at the time — that old number was substantially an artefact of the bug, not real ranking ability.

Feature engineering

A cross-window feature was detecting the loop, not the attack

The original mimicry profile cycled a 27-key script ~3 times. Any repeated loop exhausts its own payload transitions — that's what payload_seq_novelty actually measured. A realistic single-shot payload (typed once, silent after) reduced detection from 100% to 5%, then a proper finite-payload fix (with post-payload silence as real signal) recovered it to 40% — the honest number for the hardest case in the corpus.

Hyperparameter tuning

A sweep recommended a change that lost five points on test

A longer sequence horizon won the selection split by one session (2%) — noise, not signal. Applied anyway, it scored five points worse on test. The tuner now computes the noise floor and requires a challenger to clear it before recommending a change.

Evaluation integrity

A leakage-detection test kept passing because it had lost the power to fail

Adding a sixth attack profile shrank per-profile sample size; the statistical critical value grew past the effect size it was meant to catch. The audit now reports UNDERPOWERED rather than a false "ok" when a check could not have failed.

Missing ablation

N2 had never been isolated — until this document's §2

Three of four novelty pillars had ablations; the per-device baseline didn't. Built one; it showed the pillar contributes nothing measurable (§2).

Infrastructure

The corpus cache could silently serve results for code that no longer existed

It checked the contract version but not the simulator or feature-extractor source. Now fingerprinted against both; it has already fired for real once this session.

Live monitoring

Nothing was actually calling the live capture path

UsbmonSource.live() existed and was referenced only in its own docstring. A full LiveMonitor loop — device discovery, kernel-timestamp windowing, idle-detach — now exists and is verified end-to-end against a recorded replay; real debugfs still needs the Linux VM.

09Honest limitations

  • Zero real hardware. Every session is synthetic. The paper's Objective 6 (Pi Pico / Digispark evaluation) remains unmet.
  • N1 and N2 are unsupported by our own ablations (§2) — built as specified, measured to contribute nothing on this corpus.
  • N3's kernel-level enforcement was never built. Correct rule generation, dry-run only, gated behind a constant that is still False.
  • Recurrence is not uniquely justified. GRU, a CNN, and gradient boosting all tie the LSTM on the identical sequence input (§6). "Temporal modelling" is supported; "LSTM specifically" is one of several equally-good choices.
  • mimicry_adaptive at 40% detection rests on a proven bound, not a tuning gap — an unbounded version of the same attack is statistically the benign keyboard process; zero of 28 features separate it. The principled next defence is cross-device correlation, outside the current single-device architecture.
  • No raw URB archive. The plan's own intent to keep raw traces alongside features was never implemented.
  • eBPF is unstarted and may remain documented future work, per the plan's own risk register.
