00The unit of evidence

Everything the system knows arrives as lines like this one, from /sys/kernel/debug/usb/usbmon/0u.

f5ca4980 3854346339 C Ii:1:003:1 0:4 8 = 00001600 00000000
f5ca4980URB tag
3854346339timestamp, µs (wraps every 71.6 min)
Ccompletion
Ii:1:003:1interrupt IN, bus 1, device 3, endpoint 1
0:4status 0, polling interval 4
8data length — 8 bytes, not 4

This exact line is why the capture layer was rewritten. The prototype parser read the polling interval as the transfer length; the two coincide for 8-byte HID reports, so simulator output never exposed it. It also silently dropped four real line forms — every submission, every uncaptured payload, control setup packets, and isochronous completions.

02Headline results

298 held-out test sessions, split by session and stratified by profile — never by window. Threshold set at a 0.1 % per-window false-positive rate on validation benign traffic only, then gated 4-of-6. The deployed model uses 27 of the 28 features; the 28th leaks the label, and finding 3 below is why.

One false positive across 178 benign test sessions (0.6 %), and a median 3.6 s from attack onset to enforcement. The whitelist scores zero by construction: every attack profile clones a VID:PID from the benign pool, which is precisely the gap behavioural monitoring exists to close.

Two changes got here. Tripling the corpus to 1,000 sessions took detection from 81.0 % to 86.7 %. A twenty-ninth feature — the first that asks a question spanning more than one window — took it the rest of the way and closed the mimicry gap entirely. A perfect score is a leakage signal far more often than a win, so the checks below are what was done before reporting it.

A perfect score is a leakage signal. Here is what was checked.

The evaluation harness prints a warning when detection hits 100 %, when it does so at zero false positives, and when no attack class is harder than any other. All three fire on this result, and they are right to. Three things were verified before it was reported:

1. The leakage audit passes. No separable duration, window-count or VID:PID axis between benign and malicious sessions — checked per profile, not just in aggregate, because that is how the last leak survived.

2. The new feature measures behaviour, not session position. This is the failure that got log_time_since_enum deleted, and the new feature has the same suspicious shape: novelty decays over a session, and malicious windows are later in a session by construction. Under positional control it holds up — benign typing stays near 0.99 at every window position while mimicry decays to 0.72, and late benign windows score 0.991 against early mimicry windows at 0.975. If that ordering ever inverts, the feature is a leak; a regression test asserts it.

3. Mimicry still costs 24.9 s to detect, against ~3.5 s for every other class. A sevenfold latency gap is what you would expect if the detection is real and hard-won. A leak would have been instant.

The caveat that remains. This feature was designed after seeing which attack we were failing, using knowledge of how the simulator builds it. That is overfitting to our own corpus and has to be declared. The defence is that the constraint is real: a keystroke-injection payload has to type specific commands, so it cannot randomise its sequence without ceasing to be a payload. The honest claim is that this raises the attacker’s cost, not that it solves the problem.

03Do the novelty claims survive contact?

Four pillars distinguish this work from LBM (Tian et al., IEEE S&P 2019), which mediates USB in-kernel using static administrator-written rules. Each needed an ablation, not an assertion.

Still not supported — and now less so. The payload modality alone matches the fused model exactly, to four decimal places, because it is the modality that carries the new sequence feature. Fusion adds nothing measurable on this corpus. Establishing N1 requires attack families that differ from benign traffic on one axis at a time; ours differ on several. Identity alone remains by far the weakest, which is the thesis restated as a measurement.

N3 — temporal modelling is the decisive pillar

Stage 1 is memoryless: it can only ask whether a given second looks odd. It catches one attack with a static per-window signature — identity_switch, at 60.9 % — and misses every one defined by a transition over time. Adding the LSTM takes overall session detection from 11.7 % to 100 %. This is the pillar the evidence supports most clearly.

Its horizon, though, was never the lever. Sweeping the sequence length across 10, 20 and 30 windows on a held-out selection split gave identical detection at every setting, while longer horizons slightly reduced AUC and pushed latency from 3.6 s to 4.8 s. The model did not need more memory; it needed a feature that carried cross-window information in the first place (finding 6).

N2 — adaptive baselines, after a repair

The per-device baseline was measurably inert until this week; see finding 3 below. With it repaired, Stage 1’s window AUC rose from 0.8894 to 0.9363.

N4 — enforcement fires from model output

Each action carries a generated rule naming the threshold that triggered it, the three features that deviated most, and the kernel command. The threshold is not a magic number: it is the probability that yields a 0.1 % false-positive rate on held-out benign traffic.

05Eight findings from measuring what had been assumed

Seven defects and the fix that came out of one of them. Each was invisible in every previously reported number, and most surfaced only by running an ablation, a sweep, or a screen whose result had already been assumed.

Finding 1 — corpus fidelity

One feature of twenty-eight carried no information at all

The simulator emitted no control transfers anywhere in the corpus, so frac_ctrl was constant zero across every window ever scored. It also emitted only completions, never submissions — a stream real usbmon cannot produce. Both are fixed; devices now enumerate properly.

Finding 2 — label leakage

A duration leak survived being fixed once

Aggregate session durations matched between benign and malicious traffic — 63.7 s against 63.9 s — which is exactly why the earlier fix looked complete. Per profile they did not: staged_delay drew from 65–85 s while every other profile drew 40–85 s, so any window past roughly 62 s was disproportionately malicious.

The audit now runs per profile, and a test re-introduces the original bug to prove the audit still catches it. An audit that cannot fail manufactures confidence rather than providing it.

Finding 3 — silent miscalibration

Pillar N2 was in the architecture and absent from the arithmetic

Features that are near-constant for a device — a keyboard’s frac_iso is always zero — collapse their running variance, so any change produces an enormous z-score. Benign device deviation had a median of 0.8, a 99th percentile of 90.8 and a maximum of 1267. Since calibration divides by that 99th percentile, the per-device term contributed about 0.009 to a score bounded at 1.0.

A variance floor fixed it. The symptom that led there was the Stage-1-only ablation reporting exactly zero detection — a number too strange to accept.

Finding 4 — a claim that did not hold

Why detection fell from 100 % before it rose to 86.7 %

The mimicry profile drew its think-pauses from a visibly different distribution than human typing, leaving a blatant timing signature in the one profile whose entire purpose is to lack one. A timing-only model therefore detected it at 100 %, every modality independently reached 100 %, and overall detection read 100 %.

The plan had claimed class_exfil was “invisible to timing features alone.” That was asserted, never measured. The ablation shows it false. Fixing the mimicry generator moved the headline figure down to 81 %; tripling the corpus then moved it back up to 86.7 % on evidence rather than on a defect.

Finding 5 — a label leak in a legitimate-looking feature

One feature encoded when our attacks start, not what devices do

A window’s time since enumeration looks like a fair signal, and in deployment it is available. But a malicious window is post-onset by definition, so it is later in its session than an average benign window. The feature therefore separates every attack class from benign traffic while encoding no behaviour at all:

What it really measures is our onset distribution, which a real attacker chooses adversarially. The deployed model now uses 27 of 28 features. Including it buys 0.0012 AUC and 0.8 % detection — reported as an ablation, not shipped.

Finding 6 — a hypothesis the sweep refuted

Mimicry does not need a longer memory. It needs a feature we do not have.

The obvious response to mimicry was more sequence horizon: its tell is a keystroke script that cycles over 24–48 keys, far longer than a ten-second window. Sweeping 10, 20 and 30 windows changed detection by nothing at all.

The reason is upstream. Exactly one of the 28 per-window features separated mimicry from benign typing, and it was the leaking session-position feature from finding 5. A one-second window holds about five mostly-distinct keystrokes, so payload novelty and repeat ratio were identical either side of onset. The script repeat is a cross-window property, and the feature vector had nowhere to put it. A longer horizon gives the model more of nothing to integrate.

Finding 7 — the fix that followed

Order is the signal, not the alphabet

The obvious cross-window feature is “have I seen this payload before?” It does not work. Human typing and a scripted payload draw keycodes from a similar alphabet, so the set of distinct payloads looks much the same for both.

What differs is order. A script cycles a fixed set of consecutive payload pairs forever; a person types novel pairs indefinitely. Feature 29 counts the fraction of a window’s payload transitions never seen earlier in the session, judged causally and carried across window boundaries:

This made the extractor stateful — one instance per device session, reset between them, or the next device inherits the previous one’s history and reads as suspiciously familiar traffic. It also forced a contract major version: the vector changed width, so every earlier checkpoint is invalid and the loader refuses them.

Finding 8 — found by looking at live data

The dashboard’s first screen said a z-score of 4,472,091

Within minutes of pointing the new dashboard at the stored alerts, it rendered a device’s evidence as late_iface_flag 4472091.23. That is not a number an operator can act on, and it was not cosmetic.

Three features are exactly constant across benign traffic — class_behaviour_mismatch, late_iface_flag and n_interfaces are zero or one for every benign device, by construction. Standardisation divided by their near-zero spread, so a single 0→1 flip became a value around 106 that swamped all twenty-nine dimensions in both the forest and the baseline. It is the same failure as finding 3, one level up.

Bounding it rather than removing it — such a feature is informative when it changes; that is the entire point of class_behaviour_mismatch — left the headline intact but collapsed the Stage-1 ablation:

Stage 1 still ranks well — its window AUC is 0.9363 — but at a tight operating point it now recovers almost nothing. That makes the case for temporal modelling stronger, not weaker.

06What this does not yet show

  • No real USB traffic. Every number here comes from synthetic sessions. The parser is validated against real kernel line formats, but a live 60 s capture on the Linux VM is still outstanding.
  • Attack families come from the code the features were designed against. Per-profile rates are optimistic by construction. Test counts are now 16–29 sessions per class, up from 7–11, so the figures are at least stable.
  • Multi-modal fusion (N1) is not supported by this evidence. The payload modality alone matches the fused model exactly. Establishing N1 needs attack families that differ from benign traffic on one axis at a time; ours differ on several.
  • Feature 29 was designed against a known failure. We knew which attack we were missing and how the simulator builds it. The constraint it exploits is real — an injection payload must type specific commands — but an adversary who pads or reorders within limits will degrade it. It raises cost; it does not solve.
  • The dashboard reads a stored run, not a live device. It is served from the same SQLite the evaluation writes, so it demonstrates the system operating over real recorded sessions — but nothing is streaming.
  • Enforcement has never executed. Every path that would write to /sys/bus/usb/…/authorized raises instead. Four independent interlocks guard it — dry-run default, a boot-keyboard allowlist, an environment kill switch, and a review flag that is still false.
  • No streaming detector. The pipeline runs offline over sessions; nothing yet holds long-lived per-device state in production.
  • eBPF is unstarted and, per the plan’s schedule, may remain documented future work.
